#### [Blocker] F-1 — Мутация состояния через HTTP GET и утечка чувствительных параметров (раздел `s-18`)
- **Агенты:** rules, compliance, distributed
- **Стандарт:** RFC 7231 / ISO 29148
- **Цитата:** > | **REST type** | GET |
- **Описание:** Эндпоинт сохранения лимита настроек использует HTTP GET с передачей идентификатора карты и суммы в URL query, нарушая RFC 7231 и создавая уязвимость утечки данных в веб-логи и кэш.
- **Рекомендация:** Перевести метод на HTTP POST/PUT с передачей параметров в теле запроса (application/json) и заголовком Idempotency-Key.
- **Вердикт арбитра:** GET-запросы не должны производить сайд-эффекты и мутировать состояние сущностей в БД. Передача параметров карты в URL противоречит PCI DSS и стандартам REST API.
- **Исправление (патч, верифицирован, раундов: 1):**
```markdown
| Поле | Значение |
| :--- | :--- |
| **Description** | Сохранение порога. Функциональные требования: чтение порога |

#### [Critical] F-2 — Возврат HTTP 200 OK при бизнес-ошибке (псевдоуспех) (раздел `s-28`)
- **Агенты:** rules, logic, distributed
- **Стандарт:** ISO/IEC/IEEE 29148 (Consistency)
- **Цитата:** > {"result":"ERROR","message":"Проверьте сумму"}
- **Описание:** При отклонении суммы или иной ошибке валидации API возвращает статус 200 OK с телом {"result":"ERROR"}, нарушая контракт HTTP и спецификацию REST.
- **Рекомендация:** Возвращать HTTP-статусы семейства 4xx (400 Bad Request или 422 Unprocessable Entity) со стандартизированным телом ошибки.
- **Вердикт арбитра:** Возврат статуса 200 OK при ошибках ломает автоматизированный мониторинг, метрики доступности, API-шлюзы и логику обработки ошибок на клиенте.
- **Исправление (патч, верифицирован, раундов: 1):**
```markdown
```json
{"result":"OK","amount":"50000","enabled":"1"}
```

**400. Bad Request.** Ответ в случае ошибки валидации параметров, например: 
```json
{"result":"ERROR","code":"INVALID_AMOUNT","message":"Проверьте сумму"}
```
**422. Unprocessable Entity.** Ответ в случае бизнес-ошибки обработки транзакции.

**401.** Ответ в случае, если запрос выполнен без необходимой авторизации.
**403.** Ответ в случае, если на указанный ресурс доступ запрещен.
**500.** Ответ в случае, если произошла внутренняя ошибка сервера.
```
- **Критерии приёмки (Gherkin):**
```gherkin
Feature: HTTP error codes for invalid requests
  Scenario: Client sends invalid amount and receives 400 status
    Given API client sends transaction request with invalid amount
    When the server validates the input data
    Then the server returns HTTP status 400 Bad Request with error body
```

#### [Critical] F-3 — Отсутствие таймаутов и политик повторных запросов (раздел `s-12`)
- **Агенты:** rules
- **Цитата:** > Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API». Повторная доставка одного события процессинга сохраняет исходный итог.
- **Описание:** В требованиях к интеграциям не регламентированы таймауты сетевых вызовов и правила обработки неопределённого состояния (UNKNOWN) между процессингом, сервисом настроек и push.
- **Рекомендация:** Определить предельные таймауты (connect/read) и политики retry/backoff для межсервисных вызовов.
- **Вердикт арбитра:** Без явных таймаутов распределённая система подвержена зависанию потоков и каскадным сбоям при деградации внешних зависимостей.
- **Исправление (патч, требует ручной проверки, раундов: 1):**
```markdown
1. Сетевые таймауты для вызовов REST API: connect timeout — 3 секунды, read timeout — 5 секунд.
2. Политика повторных запросов (Retry/Backoff): при получении кодов ошибок 5xx или тайм-аута допускается до 3 повторных попыток с экспоненциальной задержкой (backoff multiplier — 2x, начальная задержка — 1 секунда).
3. Обработка неопределенного состояния (UNKNOWN): при отсутствии подтверждения от процессинга или сервиса push по истечении таймаута транзакция переводится в статус UNKNOWN с обязательным запуском компенсирующего запроса (status inquiry) перед фиксацией конечного статуса.
```
- **Критерии приёмки (Gherkin):**
```gherkin
Given сервис инициирует REST-запрос к процессору
When тайм-аут соединения превышает 3 секунды
Then система производит повторный вызов с экспоненциальной задержкой
```
