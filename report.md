#### [Critical] F-2 — Псевдоуспех HTTP 200 OK при бизнес-ошибке (раздел `s-28`)
- **Агенты:** rules, logic, distributed, checklist
- **Стандарт:** ISO/IEC/IEEE 29148 (Consistency)
- **Цитата:** > {"result":"ERROR","message":"Проверьте сумму"}
- **Описание:** Возврат статуса 200 OK при ошибках валидации и бизнес-логики с телом result: ERROR маскирует сбои от систем мониторинга и шлюзов.
- **Рекомендация:** Возвращать статус 400 Bad Request или 422 Unprocessable Entity со стандартным форматом ошибки при неуспешной валидации.
- **Вердикт арбитра:** Дубликаты объединены. Антипаттерн ломает мониторинг и противоречит RFC и стандартам проектирования банковских API.
- **Исправление (патч, требует ручной проверки, раундов: 1):**
```markdown
1. Успешный ответ (200 OK):
```json
{"result":"OK","amount":"50000","enabled":"1"}
```

2. Ошибка валидации или бизнес-логики (400 Bad Request):
```json
{"result":"ERROR","message":"Проверьте сумму"}
```

**401.** Ответ в случае, если запрос выполнен без необходимой авторизации.
**403.** Ответ в случае, если на указанный ресурс доступ запрещен.
**422.** Ответ в случае несоответствия данных бизнес-правилам.
**500.** Ответ в случае, если произошла внутренняя ошибка сервера.
```
- **Критерии приёмки (Gherkin):**
```gherkin
Given клиент отправляет запрос с неверной суммой
When API обрабатывает запрос
Then система возвращает статус 400 Bad Request и JSON с текстом ошибки
```

#### [Critical] F-3 — Отсутствие тайм-аутов и регламента обработки неопределенных состояний (раздел `s-12`)
- **Агенты:** rules, distributed
- **Стандарт:** ISO/IEC/IEEE 29148:2018, CHK-02
- **Цитата:** > Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API». Повторная доставка одного события процессинга сохраняет исходный итог.
- **Описание:** В требованиях к интеграции не регламентированы таймауты внешних вызовов (процессинг, push), число ретраев и обработка статуса UNKNOWN.
- **Рекомендация:** Описать SLA, таймауты на каждый внешний вызов, политики retry с exponential backoff и окно дедупликации событий.
- **Вердикт арбитра:** В распределенных финансовых системах отсутствие регламента сбоев приводит к зависанию очередей и пропуску событий.
- **Исправление (патч, требует ручной проверки, раундов: 1):**
```markdown
Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API» с жестким тайм-аутом внешних вызовов 5 секунд и политикой повторов до 3 попыток с экспоненциальной задержкой (exponential backoff). Все запросы на изменение настроек требуют передачи заголовка Idempotency-Key (UUID) с окном дедупликации 24 часа. При получении статуса UNKNOWN или сбое сети транзакция переводится в неопределенное состояние с фиксацией в журнале ошибок и последующей асинхронной сверкой статусов.
```
- **Критерии приёмки (Gherkin):**
```gherkin
Given внешняя система процессинга недоступна
When приложение отправляет запрос на изменение настроек с заголовком Idempotency-Key
Then система возвращает ошибку таймаута через 5 секунд
And выполняет повторный запрос с тем же Idempotency-Key без дублирования операции на стороне сервера
```

#### [Major] F-4 — Отсутствие механизма идемпотентности мутирующего API (раздел `s-12`)
- **Агенты:** rules, distributed
- **Стандарт:** ISO/IEC/IEEE 29148:2018, CHK-01
- **Цитата:** > Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API». Повторная доставка одного события процессинга сохраняет исходный итог.
- **Описание:** Для операции изменения настроек лимита не предусмотрен заголовок идемпотентности, что при сетевых сбоях и повторах может приводить к гонкам состояний.
- **Рекомендация:** Ввести заголовок Idempotency-Key (UUID) для изменения настроек и регламентировать срок хранения ключа.
- **Вердикт арбитра:** Критичность снижена с Blocker до Major, так как операция перезаписи порога по своей сути является семантически замещающей, однако отсутствие механизма дедупликации запросов несет риски.

#### [Major] F-6 — Несогласованность единиц измерения денежных величин (раздел `s-11`)
- **Агенты:** checklist
- **Стандарт:** ISO/IEC/IEEE 29148 / FinTech Checklist CHK-06
- **Цитата:** > Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге.
- **Описание:** Порог задается в тенге, а сумма покупки хранится в тиынах, что повышает риск ошибок конвертации и округления.
- **Рекомендация:** Унифицировать хранение и передачу всех денежных сумм в минимальных единицах (тиынах) либо зафиксировать жесткие правила конвертации.
- **Вердикт арбитра:** Смешивание тенге и тиынов в одной модели данных часто приводит к расхождениям счетчиков.
- **Исправление (патч, верифицирован, раундов: 1):**
```markdown
Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тиынах.
```
- **Критерии приёмки (Gherkin):**
```gherkin
Given пользователь настраивает порог в системе
When значение порога задается в тенге
Then система автоматически конвертирует и сохраняет порог в тиынах для соответствия единице измерения суммы покупки
```
