#### [Blocker] F-1 — Мутация состояния данных через HTTP GET с утечкой параметров в query (раздел `s-18`)
- **Агенты:** rules, compliance
- **Стандарт:** RFC 7231 / ISO 29148
- **Цитата:** > | **REST type** | GET |
- **Описание:** Эндпоинт изменения порога /alerts/saveLimit использует HTTP GET с передачей cardId и amount в строке запроса, что нарушает RFC 7231 и требования безопасности PCI DSS из-за кэширования и логирования URL.
- **Рекомендация:** Заменить HTTP метод на POST или PUT, передавать параметры cardId, amount и enabled в теле запроса формата application/json.
- **Вердикт арбитра:** Использование GET для изменения состояния БД является грубым архитектурным дефектом и создает критическую уязвимость утечки параметров карты в логи веб-серверов и прокси.
- **Исправление (патч, верифицирован, раундов: 1):**
```markdown
| Поле | Значение |
| :--- | :--- |
| **Description** | Сохранение порога. Функциональные требования: чтение и сохранение порога с ограничением частоты запросов |

| **CURL** | `curl -X POST "$BASE/alerts/saveLimit" -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"cardId":"demo-42","amount":50000,"enabled":1}'` |
| **Swagger** | — |
```

#### [Critical] F-3 — Отсутствие спецификации тайм-аутов и обработки статуса UNKNOWN (раздел `s-12`)
- **Агенты:** rules, checklist
- **Стандарт:** ISO/IEC/IEEE 29148 / FinTech Checklist CHK-02
- **Цитата:** > Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API». Повторная доставка одного события процессинга сохраняет исходный итог.
- **Описание:** В интеграционных требованиях между сервисом расходов, карточным процессингом и push-сервисом не заданы сетевые тайм-ауты и сценарии поведения при недоступности внешних сервисов.
- **Рекомендация:** Определить явные тайм-ауты (connect/read) для вызовов сервиса push и настроек, а также регламент повторных попыток с экспоненциальной задержкой.
- **Вердикт арбитра:** Без регламента тайм-аутов интеграции зависают в неопределенном состоянии при сбоях брокера или шлюзов.
- **Исправление (патч, требует ручной проверки, раундов: 1):**
```markdown
1. Интеграция с сервисом пуш-уведомлений и процессингом реализуется с жесткими сетевыми тайм-аутами: connect timeout — 2 с, read timeout — 5 с. При получении сетевой ошибки или статуса UNKNOWN инициируется повторная доставка (retry) с экспоненциальной задержкой (до 3 попыток).
2. Все запросы на сохранение параметров и настроек через REST API должны содержать обязательный заголовок Idempotency-Key. Бэкенд обеспечивает дедупликацию запросов в течение скользящего окна 24 часа.
3. Согласование и утверждение интеграционной спецификации: [ТРЕБУЕТ ЗАПОЛНЕНИЯ ОТВЕТСТВЕННЫМ]. Обязательное условие подписания — успешное прохождение интеграционного тестирования по сценариям тайм-аутов и дублирования запросов.
```
- **Критерии приёмки (Gherkin):**
```gherkin
Given сервис пуш-уведомлений недоступен или возвращает таймаут
```


#### [Major] F-5 — Отсутствие механизма идемпотентности при сохранении параметров (раздел `s-12`)
- **Агенты:** rules, distributed
- **Стандарт:** CHK-01 (Идемпотентность)
- **Цитата:** > Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API». Повторная доставка одного события процессинга сохраняет исходный итог.
- **Описание:** В контракте API сохранения лимита не предусмотрен заголовок идемпотентности (Idempotency-Key), что при сетевых тайм-аутах или повторных запросах создает риск дублирования операций.
- **Рекомендация:** Добавить обязательный заголовок Idempotency-Key в спецификацию запроса сохранения настроек и зафиксировать окно дедупликации на бэкенде.
- **Вердикт арбитра:** Сохранение порога является операцией типа upsert (замена текущего значения), поэтому критичность снижена с Blocker до Major: повторный вызов заменяет то же значение, однако явный ключ требуется для надежной защиты от race conditions.

#### [Major] F-6 — Пустой раздел спецификации с заглушкой тестирования (раздел `s-14`)
