### [Critical] F-2 — Псевдоуспех HTTP 200 OK при возникновении бизнес-ошибки (раздел `s-28`)
- **Агенты:** rules, logic, qa
- **Стандарт:** ISO/IEC/IEEE 29148 (Consistency)
- **Цитата:** > {"result":"ERROR","message":"Проверьте сумму"}
- **Описание:** При отклонении валидации метод возвращает HTTP-статус 200 с телом result: ERROR вместо валидного 4xx статуса, ломая мониторинг и контрактную интеграцию.
- **Рекомендация:** Использовать стандартный статус HTTP 400 Bad Request или 422 Unprocessable Entity для ответов с бизнес-ошибками валидации.
- **Вердикт арбитра:** Прямое нарушение REST-конвенций и стандартов проектирования API. Дубликаты от критиков правил, логики и QA объединены.
- **Исправление (патч, верифицирован, раундов: 1):**
```markdown
```json
{"result":"OK","amount":"50000","enabled":"1"}
```

**400. Bad Request.** Ответ в случае ошибки валидации параметров.

**401. Unauthorized.** Ответ в случае, если запрос выполнен без необходимой авторизации.

**403. Forbidden.** Ответ в случае, если на указанный ресурс доступ запрещен.

**422. Unprocessable Entity.** Ответ в случае бизнес-ошибки.

**500. Internal Server Error.** Ответ в случае, если произошла внутренняя ошибка сервера.
```
- **Критерии приёмки (Gherkin):**

### [Critical] F-3 — Отсутствие параметров таймаутов и политики ретраев для интеграций (раздел `s-12`)
- **Агенты:** rules
- **Цитата:** > Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API». Повторная доставка одного события процессинга сохраняет исходный итог.
- **Описание:** В разделе интеграции не описаны таймауты сетевых взаимодействий с процессингом, сервисом настроек и push-шлюзом, а также правила повтора запросов.
- **Рекомендация:** Определить сетевые таймауты (connect/read) и политику exponential backoff для вызовов внешних сервисов.
- **Вердикт арбитра:** Критично для распределенных интеграций банковского ПО во избежание зависания потоков и каскадных сбоев.
- **Исправление (патч, верифицирован, раундов: 1):**
```markdown
Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API» с сетевыми таймаутами 3000 мс на подключение и 5000 мс на чтение, а также политикой повтора запросов с экспоненциальной задержкой (exponential backoff) до 3 попыток. Запросы на сохранение параметров содержат обязательный заголовок Idempotency-Key для защиты от дублирования сетевых вызовов. Повторная доставка одного события процессинга сохраняет исходный итог.
```
- **Критерии приёмки (Gherkin):**

### [Major] F-4 — Отсутствие идемпотентности при сохранении параметров (раздел `s-12`)
- **Агенты:** rules, distributed
- **Стандарт:** CHK-01 (Идемпотентность)
- **Цитата:** > Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API». Повторная доставка одного события процессинга сохраняет исходный итог.
- **Описание:** В спецификации эндпоинта сохранения порога отсутствует требование заголовка идемпотентности (Idempotency-Key) для защиты от повторных сетевых вызовов.
- **Рекомендация:** Описать обязательный заголовок Idempotency-Key и логику дедупликации повторных сетевых вызовов сохранения настроек.
- **Вердикт арбитра:** Снижено с Blocker до Major: сохранение лимита перезаписывает состояние (хотя при сетевых гонках важен ключ), но реального списания средств в данном вызове не происходит.

### [Minor] F-6 — Некорректный статус HTTP 404 вместо 403 при доступе к чужой карте (раздел `s-31`)
- **Агенты:** logic
- **Стандарт:** ISO/IEC/IEEE 29148 / CHK-07
- **Цитата:** > Для чужой карты возвращается 404, как и для отсутствующей карты.
- **Описание:** При обращении к чужой карте спецификация требует возвращать статус 404 вместо 403 Forbidden, нарушая спецификацию REST-контроля доступа.
- **Рекомендация:** Регламентировать разграничение кодов 403 Forbidden (чужой ресурс) и 404 Not Found (несуществующий ресурс) либо зафиксировать политику скрытия ресурсов для ИБ.
- **Вердикт арбитра:** Возврат 404 часто применяется как защита от перебора ресурсов, однако в ТЗ логика смешана и не формализована должным образом.
- **Исправление (патч, верифицирован, раундов: 1):**
```markdown
Для чужой карты возвращается 403 Forbidden, в то время как для несуществующей карты возвращается 404 Not Found.
**403**
```json
{"message":"Доступ запрещен"}
```
**404**
```json
{"message":"Карта не найдена"}
```
```
- **Критерии приёмки (Gherkin):**
```gherkin
Given авторизованный пользователь запрашивает данные чужой карты
When отправляется запрос на получение карты

```

### [Minor] F-7 — Размытые нефункциональные требования и нехватка числовых метрик SLA/RPS (раздел `s-10`)

- **Описание:** Формулировка «в течение минуты» не содержит измеримых метрик задержки (p95/p99) и не определяет требования к пропускной способности (RPS) и доступности.
- **Рекомендация:** Указать конкретные метрики p95 latency обработки событий и целевой SLA/RPS сервиса уведомлений.
- **Вердикт арбитра:** Замечания трех критиков объединены. Дефект относится к формулировкам NFR согласно шкале Minor.
- **Исправление (патч, верифицирован, раундов: 1):**
```markdown

```
