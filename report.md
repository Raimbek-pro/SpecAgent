#### [Blocker] F-1 — Мутация состояния через метод HTTP GET (раздел `s-18`)
- **Агенты:** rules, compliance
- **Стандарт:** RFC 7231 / ISO 29148
- **Цитата:** > | **REST type** | GET |
- **Описание:** Эндпоинт изменения порога и настроек уведомлений использует HTTP GET с передачей параметров в Query, что противоречит RFC 7231 и приводит к утечке данных в веб-логи.
- **Рекомендация:** Перевести метод на HTTP POST или PUT и передавать изменяемые параметры в теле запроса (application/json).
- **Вердикт арбитра:** Критический дефект архитектуры и безопасности API, классифицируемый как Blocker согласно правилам аудита.
- **Исправление (патч, верифицирован, раундов: 1):**
```markdown
| Поле | Значение |
| :--- | :--- |
| **Description** | Сохранение порога. Функциональные требования: чтение и изменение порога |

#### [Critical] F-2 — Возврат статуса 200 OK при бизнес-ошибке (псевдоуспех) (раздел `s-28`)
- **Агенты:** rules, logic, distributed
- **Стандарт:** ISO/IEC/IEEE 29148 (Consistency)
- **Цитата:** > {"result":"ERROR","message":"Проверьте сумму"}
- **Описание:** При ошибке валидации суммы эндпоинт возвращает HTTP 200 с телом {'result':'ERROR'}, нарушая семантику протокола HTTP.
- **Рекомендация:** Возвращать статус 400 Bad Request или 422 Unprocessable Entity со стандартизированным объектом описания ошибки.
- **Вердикт арбитра:** Прямое нарушение консистентности API и стандартов обработки ошибок, усложняющее интеграцию и мониторинг.
- **Исправление (патч, требует ручной проверки, раундов: 1):**
```markdown
**400.** Неверный формат запроса или ошибка валидации бизнес-правил (например, некорректная сумма).
```json
{"error": {"code": "INVALID_AMOUNT", "message": "Проверьте сумму"}}
```

**401.** Ответ в случае, если запрос выполнен без необходимой авторизации.

**403.** Ответ в случае, если на указанный ресурс доступ запрещен.

**422.** Ошибка обработки данных.

**500.** Ответ в случае, если произошла внутренняя ошибка сервера.
```
- **Критерии приёмки (Gherkin):**
```gherkin
Given пользователь отправляет запрос с некорректной суммой
When система выполняет валидацию запроса
Then система возвращает HTTP статус 400 Bad Request с описанием ошибки
```

#### [Critical] F-3 — Отсутствие параметров таймаутов и политики повторов (Retry) (раздел `s-12`)
- **Агенты:** rules
- **Цитата:** > Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API». Повторная доставка одного события процессинга сохраняет исходный итог.
- **Описание:** Для интеграций между карточным процессингом, сервисом настроек и push-шлюзом не определены таймауты и правила обработки сетевых сбоев.
- **Рекомендация:** Указать предельные тайм-ауты (connect/read) для каждого межсервисного вызова и стратегию retry с экспоненциальной задержкой.
- **Вердикт арбитра:** Отсутствие таймаутов в распределенных банковских цепочках создает риск зависания потоков и потери сообщений.
- **Исправление (патч, верифицирован, раундов: 1):**
```markdown
1. Межсервисные взаимодействия выполняются со следующими параметрами надежности и таймаутов:
- Подключение (connect timeout): 3000 мс.
- Чтение (read timeout): 5000 мс.
- Политика повторов (Retry): экспоненциальная задержка (backoff) с коэффициентом 2, максимальное число попыток — 3.

Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API». Повторная доставка одного события процессинга сохраняет исходный итог.
```
- **Критерии приёмки (Gherkin):**
```gherkin
Given сервис интеграции отправляет событие в процессинг
When происходит сетевой сбой или таймаут соединения
Then система повторяет запрос до 3 раз с экспоненциальной задержкой
```

#### [Major] F-6 — Несоответствие типов данных параметра amount между запросом и ответом (раздел `s-24`)
- **Агенты:** logic
- **Стандарт:** ISO/IEC/IEEE 29148 / Data Types
- **Цитата:** > `amount` | integer | 32 bit | Да | 1 000–1 000 000 | Порог в тенге | `limit_kzt`
- **Описание:** В Query-параметрах amount заявлен как integer (32 bit), а в схеме ответа описан со строковым типом данных (string).
- **Рекомендация:** Унифицировать тип поля amount в контракте API, сделав его целочисленным (integer) во всех блоках.
- **Вердикт арбитра:** Противоречие в типах контракта приводит к десериализационным ошибкам клиентских приложений.
- **Исправление (патч, верифицирован, раундов: 1):**
```markdown
| Parameter | Format | Size | Mandatory | Logic | Description | DB field |

| `amount` | integer | 32 bit | Да | 1 000–1 000 000 | Порог в тенге (целое число) | `limit_kzt` |

#### [Major] F-7 — Рассинхронизация единиц учета денежных сумм (раздел `s-11`)
- **Агенты:** checklist
- **Стандарт:** ISO/IEC/IEEE 29148 / FinTech Checklist CHK-06
- **Цитата:** > Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге.
- **Описание:** Суммы покупок сохраняются в тиынах, тогда как порог расходов и поле amount API задаются в тенге, что создает риск ошибок округления и сдвига порядков при сравнении.
- **Рекомендация:** Привести все денежные значения к минимальной неделимой единице (тиын) либо явно специфицировать логику конвертации при валидации порога.
- **Вердикт арбитра:** Финансовые расчеты требуют единой размерности для предотвращения логических багов подсчета.
- **Исправление (патч, верифицирован, раундов: 1):**
```markdown
Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог расходов в тиынах (целое число, умноженное на 100). При сравнении суммы покупки с порогом расхода конвертация не требуется.
```
- **Критерии приёмки (Gherkin):**
```gherkin
Given сумма покупки равна 150000 тиын
And порог расходов задан как 150000 тиын
When система проверяет превышение порога
Then сравнение выполняется корректно без погрешностей округления
```

#### [Major] F-8 — Отсутствие негативных сценариев в критериях приемки (раздел `s-15`)
- **Агенты:** qa
- **Стандарт:** CHK-10 (Полнота критериев приемки — ISO 29148)
- **Цитата:** > | Расходы 48 500 ₸, порог 50 000 ₸ | Провести покупку на 1 500 ₸ | Итог 50 000 ₸ и один push |
- **Описание:** Критерии приемки включают исключительно успешные варианты поведения и не описывают реакции системы на ошибочный ввод или недопустимые диапазоны порогов.
- **Рекомендация:** Добавить сценарии критериев приемки для граничных значений (менее 1000 ₸, более 1 000 000 ₸, отрицательные значения, неактивные карты).
- **Вердикт арбитра:** Без негативных критериев приемки невозможно полноценно протестировать граничные условия бизнес-логики.
- **Исправление (патч, верифицирован, раундов: 1):**
```markdown
| Исходные условия | Действие | Ожидаемый результат |
| :--- | :--- | :--- |
| Расходы 48 500 ₸, порог 50 000 ₸ | Провести покупку на 1 500 ₸ | Итог 50 000 ₸ и один push |
| Покупка 31 января в 23:58 на 4 000 ₸ | Провести 1 февраля в 00:03 по Алматы | Февральский счётчик вырос на 4 000 ₸ |
| Расходы 19 900 ₸, порог 20 000 ₸ | Перевести 500 ₸ | Счётчик показывает 19 900 ₸ |
| Баланс 0 ₸, порог 50 000 ₸ | Попытка провести покупку на -500 ₸ | Ошибка валидации 400 Bad Request, счётчик не изменен |
| Карта заблокирована | Попытка провести покупку на 1 000 ₸ | Отказ транзакции, push-уведомление не отправляется |
```
- **Критерии приёмки (Gherkin):**
```gherkin
Given пользователь имеет активный лимит расходов
When выполняется попытка провести транзакцию с отрицательной суммой
Then система возвращает ошибку валидации и сохраняет текущее состояние счетов
```
